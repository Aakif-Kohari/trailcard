# TrailCard design notes

## Goal

Make the screen the shortest part of a hike. TrailCard front-loads all the thinking into a couple of minutes at a laptop and hands you a printed page, so the phone can stay in your pocket.

## Principles

1. **Numbers come from code, words come from the model.** Time, daylight and water are safety-relevant, so they are calculated deterministically in `planner.py`. The model receives them as JSON and writes advice around them.
2. **Fail safe and fail offline.** If Ollama is missing, slow or wrong, the card is still produced from a deterministic template. A hiker should never be left without a card because an AI call failed.
3. **Show the model's limits.** The card says whether the advice came from a model or from the template, and the numbers table is always generated by code.
4. **Open and local.** Open-weight models via Ollama mean no API key, no per-use cost, no network dependency on the trail, and no location data sent to a third party. Swapping models is a dropdown.

## Pipeline

1. `app.py` collects inputs. A GPX file (parsed by `gpx_utils.py`) overrides the typed distance and climb.
2. `planner.compute_plan` returns one dictionary: walking time, total time with breaks, sunrise and sunset, latest safe start, planned finish, halfway time, hard turnaround time, water, and any warnings.
3. `llm.generate_card` sends that dictionary to the local model with a strict system prompt (plain text, six named sections, use only the given facts).
4. The answer is checked:
   - **Time check:** every `HH:MM` in the answer must exist in the plan, otherwise the answer is rejected.
   - **Structure check:** the answer is parsed into the six sections. Fewer than three recognised sections means rejection. One or two missing sections are filled from the template.
5. `render.render_card_html` combines the plan table and card sections into a print-friendly A4 page.

## Planning model

| Quantity | Formula |
| --- | --- |
| Walking time | distance / 5 km/h + ascent / 10 m x 1 min (Naismith's rule) |
| Total time | walking time + planned breaks |
| Target finish | sunset - 1 hour |
| Latest safe start | target finish - total time |
| Hard turnaround | target finish - total time / 2 |
| Water per person | 0.5 L per hour of total time, rounded up to 0.5 L |

The hard turnaround is the latest time to be at the halfway point (far end of an out-and-back, midpoint of a loop). It assumes the second half takes about as long as the first, which is conservative for descents and optimistic for tired groups.

## GPX elevation gain

GPS altitude is noisy. Summing every small up-tick overstates the climb, sometimes by a large factor. `gpx_utils.elevation_gain` uses a hysteresis filter: the reference elevation only moves after a change of at least 3 m.

## Time zones

Offline time zone lookup needs extra data (and often an extra dependency), so TrailCard asks for the UTC offset directly. Sunrise and sunset are computed from latitude, longitude and date, then expressed in that offset. A wrong offset shifts every clock time, so the form explains it and the card prints the offset it used.

## Known limitations

- Naismith's rule ignores terrain, load, fitness and weather.
- Polar day and night have no usable sunset, so planning is refused with a clear message.
- The time guardrail does not verify distances or other numbers in the model's prose.
- Ollama calls are mocked in the automated tests. Behaviour with a real model depends on the model and its version.
- TrailCard does not fetch weather or trail conditions. That would need the internet, which is the opposite of the point.

## Ideas for later

- Optional offline elevation profile drawn from the GPX file.
- A small QR code on the card containing the plan as JSON.
- Multi-language cards using multilingual open-weight models.
